# TaskFlow RAG — Контрольні результати AFTER RAG

## Методика і статус виконання

Для кожного Q01–Q10 викликано `taskflow-vault.search_notes` рівно один раз, строго послідовно, передаючи незмінний текст запитання з `evaluation-questions.md`. Усі десять викликів повернули результати пошуку. Технічних помилок і повторів не було. Нижче наведено повернуті MCP-фрагменти з шляхами, номерами і відстанями. Якщо MCP обрізав фрагмент, обрізання збережене.

Оцінка 0 означає, що серед повернутого контексту немає релевантної інформації; 1 — релевантна, але неповна; 2 — достатня для правильної відповіді з підтвердженням. Не трактуємо малу відстань як доказ релевантності. Для Q10 відсутність підтвердження API в результатах не означає доказу відсутності рішення у всій базі.

## Q03 — SQLite Architecture

**Запитання:** Чому для локального зберігання завдань обрано SQLite?

**Результати MCP:**

- `Decisions/SQLite Storage Decision.md`, фрагмент 1, відстань **0.3264**: контекст — застосунок має зберігати завдання між запусками, отже потрібне локальне сховище даних.
- `Decisions/SQLite Storage Decision.md`, фрагмент 3, відстань **0.3928**: `## Прийняте рішення` / `Для збереження завдань обрано SQLite.`
- `Decisions/User Settings Storage.md`, фрагмент 7, відстань **0.4109**: rationale — вимога до SQLite стосується завдань; для невеликого локального набору налаштувань немає потреби у реляційних запитах чи спільних транзакціях; JSON зберігає просту межу конфігурації і предметних даних без окремої системи чи залежностей. Кінець отриманого фрагмента обрізано: `...активної підтримки багатьох ко`.
- `Decisions/SQLite Storage Decision.md`, фрагмент 5, відстань **0.4623**: доступ до БД буде через Task Repository; структуру записів визначатиме Task Model; основна сутність БД — Task.
- `Decisions/SQLite Storage Decision.md`, фрагмент 4, відстань **0.4764**: SQLite не потребує окремого сервера, підтримує SQL-запити і входить до стандартної бібліотеки Python через `sqlite3`; для невеликого локального застосунку її можливостей достатньо.

**Оцінка:** **2/2**.

**Відповідь і підстава:** Потрібне локальне сховище для збереження завдань між запусками. SQLite обрано, бо вона не потребує окремого сервера, підтримує SQL і доступна через стандартний модуль Python `sqlite3`; її можливостей достатньо для невеликого локального застосунку. Рішення й rationale підтверджені фрагментами 1, 3 і 4 `Decisions/SQLite Storage Decision.md`.

## Q08 — User Settings Storage

**Запитання:** Чому налаштування користувача вирішили зберігати в JSON, а завдання — у SQLite?

**Результати MCP:**

- `Decisions/User Settings Storage.md`, фрагмент 7, відстань **0.5548**: для невеликого локального набору налаштувань не виявлено потреби в реляційних запитах або спільних транзакціях із завданнями; JSON підтримує просту межу між конфігурацією та предметними даними без окремої системи чи залежностей. Фрагмент обрізаний наприкінці.
- `Decisions/User Settings Storage.md`, фрагмент 6, відстань **0.6620**: рішення сформульоване як **запропоновано** зберігати налаштування в окремому JSON у каталозі конфігурації; вони не зберігатимуться в SQLite і не змінюватимуть спосіб зберігання завдань. Також зазначено вимоги до перевірки структури, збереження невідомих параметрів, атомарного запису й явного повідомлення помилок.
- `Decisions/SQLite Storage Decision.md`, фрагмент 1, відстань **0.6961**: для збереження завдань між запусками необхідне локальне сховище.
- `Decisions/SQLite Storage Decision.md`, фрагмент 2, відстань **0.7451**: JSON простий, але незручний для складніших пошукових операцій та оновлень; SQLite — локальна реляційна база без окремого сервера; PostgreSQL потребує додаткового налаштування.
- `Decisions/SQLite Storage Decision.md`, фрагмент 3, відстань **0.7787**: прийняте рішення — зберігати завдання в SQLite.

**Оцінка:** **2/2**.

**Відповідь і підстава:** Для завдань є окреме прийняте рішення використовувати SQLite. Для невеликого набору налаштувань не потрібні реляційні запити чи спільні транзакції, тому JSON пропонує просте відокремлення конфігурації від предметних даних без зайвої залежності. Важливе уточнення: фрагмент про JSON позначає цей варіант як **запропонований**, а не підтверджує його як затверджене архітектурне рішення. Обґрунтування містять `Decisions/User Settings Storage.md` і `Decisions/SQLite Storage Decision.md`.

## Q10 — Missing Decision

**Запитання:** Чи є в базі знань затверджене рішення використовувати SQLite Backup API для резервного копіювання TaskFlow?

**Результати MCP:**

- `Decisions/SQLite Storage Decision.md`, фрагмент 1, відстань **0.6212**: застосунок має зберігати завдання між запусками; потрібне локальне сховище.
- `Decisions/User Settings Storage.md`, фрагмент 5, відстань **0.6756**: серед переваг зберігання налаштувань у таблиці SQLite — їх включення до спільного резервного копіювання бази; також наведені недоліки такого варіанта.
- `Decisions/User Settings Storage.md`, фрагмент 8, відстань **0.6905**: уривок про умови повторної оцінки SQLite, зокрема транзакційну узгодженість та підтримку багатьох користувачів.
- `Decisions/User Settings Storage.md`, фрагмент 7, відстань **0.7097**: rationale JSON для налаштувань; кінець фрагмента обрізано.

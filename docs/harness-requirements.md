# Вимоги до Agent Harness для TaskFlow

## 1. Призначення Agent Harness

Agent Harness  інженерна інфраструктура, яка забезпечує контрольовану роботу ШІ-агента під час розробки застосунку TaskFlow.

Harness надає агенту доступ до інформації про проєкт, визначає типові процедури розробки та встановлює обмеження на автономне виконання дій.

Головна мета  прискорення розробки TaskFlow зі збереженням контролю над змінами, які вносить агент.

## 2. Обрана агентна IDE

Середовище: Visual Studio Code.

Агентний інструмент: GitHub Copilot.

Обґрунтування вибору:

- Підтримка роботи з файлами проєкту.
- Можливість виконання команд у терміналі.
- Інтеграція із Git та GitHub.
- Підтримка Model Context Protocol (MCP).
- Можливість використання Agent Skills.
- Підтримка проєктних інструкцій і агентних ролей.
- Наявність механізму hooks для контролю дій агента.

Для роботи використовуватиметься агентний режим, що дозволяє виконувати багатокрокові задачі розробки.

## 3. Джерела даних

Harness повинен використовувати такі джерела інформації:

### 3.1. Документація застосунку

Файли docs/app-requirements.md та docs/harness-requirements.md містять вимоги до застосунку й інфраструктури агента.

### 3.2. Вихідний код

Програмні модулі TaskFlow надають інформацію про реалізовані функції, структуру проєкту та залежності.

### 3.3. GitHub

GitHub використовується для збереження вихідного коду, історії комітів та інформації про зміни.

### 3.4. База знань Obsidian

Окремий Obsidian vault зберігатиме знання про архітектуру, компоненти, терміни й технічні рішення TaskFlow.

Доступ агента до vault здійснюватиметься через MCP-конектор.

### 3.5. Результати тестування

Журнали pytest використовуватимуться для аналізу помилок і перевірки змін у програмному коді.

## 4. Цільові задачі агента

### TASK-01. Генерація програмних модулів

Агент допомагає створювати модулі TaskFlow відповідно до затвердженої архітектури та вимог застосунку.

### TASK-02. Генерація автоматизованих тестів

Агент створює unit-тести для перевірки основних функцій TaskFlow із використанням pytest.

### TASK-03. Перевірка програмного коду

Агент аналізує код, знаходить потенційні помилки, перевіряє відповідність архітектурі та пропонує покращення.

### TASK-04. Оновлення бази знань

Після завершення значущих змін агент створює або оновлює відповідні нотатки у vault через MCP-конектор.

### TASK-05. Аналіз помилок

Агент аналізує повідомлення про помилки та результати тестування, визначає можливі причини збоїв і пропонує способи виправлення.

## 5. Первинні Guardrails

Guardrails визначають обмеження на автономні дії агента.

### 5.1. Allow - дозволені дії

- Читання вихідного коду застосунку.
- Перегляд документації та вимог.
- Аналіз результатів тестування.
- Пошук інформації в базі знань.
- Формування рекомендацій без зміни файлів.

### 5.2. Warn / Require Approval - потребують підтвердження

- Зміна існуючих програмних модулів.
- Видалення або перейменування файлів застосунку.
- Внесення архітектурних змін.
- Створення Git-комітів та виконання push.
- Оновлення важливих нотаток бази знань.

### 5.3. Block - заборонені дії

- Видалення всього репозиторію або бази знань.
- Використання git push --force для захищеної гілки.
- Видалення історії архітектурних рішень.
- Запис секретних ключів і токенів у репозиторій.
- Вимкнення механізмів захисту без дозволу розробника.

## 6. Архітектура Harness

Harness складається з таких компонентів:

1. Agent IDE - середовище виконання ШІ-агента.
2. Data Sources - вихідний код, документація, GitHub і результати тестування.
3. Knowledge Layer - база знань Obsidian.
4. MCP Connectors - інструменти обміну даними між агентом і зовнішніми джерелами.
5. Skills - повторно використовувані процедури розробки.
6. Guardrails та Hooks - правила й технічні механізми контролю дій.
7. Orchestration - координація кількох агентних ролей.
8. Evaluation - оцінювання правильності й надійності роботи агента.

## 7. Початкові критерії оцінювання

Для перевірки якості harness використовуватимуться:

- Частка успішно виконаних задач агента.
- Кількість виявлених порушень guardrails.
- Коректність створених програмних модулів.
- Результати автоматизованих тестів.
- Точність отримання інформації з бази знань.
- Кількість випадків, коли знадобилося ручне втручання.

## 8. Організація репозиторіїв

Для проєкту використовуються два окремі GitHub-репозиторії.

taskflow-app:
- Код застосунку.
- Документація.
- MCP-сервер.
- Guardrails та hooks.
- Skills.
- Оркестрація.
- Автоматизовані тести.

taskflow-knowledge-base:
- Concepts/.
- Components/.
- Decisions/.
- Glossary/.
- MOC-нотатки.

База знань фізично розміщується поза робочою директорією застосунку.

Взаємодія агента з базою знань здійснюється через зареєстровані MCP-інструменти.

## 9. Очікуваний результат

Результатом розробки стане Agent Harness, який допомагатиме створювати й перевіряти програмні компоненти TaskFlow, використовувати знання про архітектуру застосунку та виконувати задачі відповідно до встановлених обмежень.


# TaskFlow Agent Orchestration Plan

## 1. Purpose

Організувати розробку функціональності TaskFlow за допомогою трьох спеціалізованих агентів: Planner, Coder і Reviewer.

Мета оркестрації - розділити аналіз вимог, реалізацію коду та перевірку результатів між різними ролями.

## 2. Development Task

Назва задачі: TaskFlow Task Management Module.

Необхідно реалізувати початкову функціональність роботи із завданнями користувача.

Базовий обсяг:
- Створення нового завдання.
- Збереження завдання в SQLite.
- Отримання списку завдань.
- Перевірка введених даних.
- Обробка помилок.
- Автоматизовані тести.

Точні функціональні вимоги необхідно звірити з docs/app-requirements.md до початку реалізації.

## 3. Agent Roles

### 3.1. Planner

Відповідальність:
- Аналіз вимог TaskFlow.
- Отримання архітектурного контексту з Obsidian.
- Визначення компонентів для реалізації.
- Декомпозиція задачі на конкретні кроки.
- Визначення критеріїв приймання.
- Формування плану для Coder.

Planner не змінює програмний код.

Результат:
docs/orchestration/planner-handoff.md

### 3.2. Coder

Відповідальність:
- Отримання та аналіз плану Planner.
- Реалізація функціональності на Python.
- Використання SQLite відповідно до архітектури.
- Створення автоматизованих тестів.
- Запуск тестів.
- Документування реалізованих змін.

Coder повинен дотримуватися Guardrails.

Coder не виконує Git push без дозволу користувача.

Результат:
docs/orchestration/coder-handoff.md

### 3.3. Reviewer

Відповідальність:
- Аналіз плану Planner.
- Перевірка реалізації Coder.
- Перевірка відповідності вимогам.
- Перевірка безпеки та Guardrails.
- Аналіз результатів тестування.
- Виявлення помилок і недоліків.
- Формування рекомендацій.

Reviewer не змінює код самостійно.

Результат:
docs/orchestration/reviewer-report.md

## 4. Handoff Mechanism

Оркестрація реалізується через послідовні сесії custom agents у GitHub Copilot.

Контекст між агентами передається через Markdown-файли в docs/orchestration/.

### Planner to Coder

Передається:
1. Опис задачі.
2. Функціональні вимоги.
3. Архітектурні обмеження.
4. Посилання на релевантні нотатки Obsidian.
5. План реалізації.
6. Обґрунтування технічних рішень.
7. Критерії приймання.
8. Відкриті питання.

### Coder to Reviewer

Передається:
1. Початковий план Planner.
2. Перелік створених і змінених файлів.
3. Опис реалізованої функціональності.
4. Обґрунтування реалізації.
5. Відхилення від плану та їх причини.
6. Результати виконання тестів.
7. Відомі обмеження.
8. Питання для перевірки Reviewer.

### Reviewer to Coder

У разі виявлення проблем передається:
1. Опис проблеми.
2. Розташування в коді.
3. Рівень важливості.
4. Причина порушення вимог.
5. Рекомендоване виправлення.
6. Умови повторної перевірки.

## 5. Agent Harness

Використовуються:

IDE: Visual Studio Code.

Agent tool: GitHub Copilot.

Knowledge base: Obsidian.

MCP: taskflow-vault.

Version control: Git and GitHub.

Skills:
- taskflow-code-review
- taskflow-adr

Guardrails:
- docs/guardrails.md
- .github/hooks/pre_tool_guardrail.py

Кожна роль повинна використовувати лише необхідні для її задачі інструменти.

## 6. Execution Workflow

1. Planner аналізує вимоги та базу знань.
2. Planner створює planner-handoff.md.
3. Користувач перевіряє план.
4. Coder читає handoff і реалізує модуль.
5. Coder створює coder-handoff.md.
6. Reviewer аналізує реалізацію та результати тестів.
7. Reviewer створює reviewer-report.md.
8. За потреби Coder виправляє знайдені помилки.
9. Reviewer повторно перевіряє виправлення.
10. Після схвалення користувача результати зберігаються в Git.

## 7. Acceptance Criteria

Оркестрація вважається успішною, якщо:

- Усі три ролі виконали свої завдання.
- Передано контекст та обґрунтування рішень.
- Реалізовано функціональність TaskFlow.
- Проведено автоматизоване тестування.
- Reviewer перевірив роботу Coder.
- Виявлені недоліки задокументовано.
- Дотримано Guardrails.
- Збережено транскрипт виконання.
- Результати закомічено до GitHub.

## 8. Restrictions

- Заборонено force push.
- Заборонено видаляти архітектурні рішення.
- Заборонено рекурсивно видаляти репозиторії.
- Запис у Obsidian потребує підтвердження.
- Git push потребує підтвердження користувача.
- Не можна вигадувати результати тестування.
- Не можна заявляти про завершення задачі без перевірки.

## 9. Documentation

Результати роботи кожної ролі документуються окремо.

Підсумковий документ повинен містити:
- Послідовність виконання.
- Результати Planner.
- Результати Coder.
- Результати Reviewer.
- Проблеми передачі контексту.
- Ручні виправлення.
- Підсумок роботи оркестрації.

# Coder Handoff

## Task

Реалізувати базовий модуль керування завданнями TaskFlow на Python і SQLite відповідно до [Planner Handoff](planner-handoff.md): створення завдань, довготривале збереження, перегляд списку, валідація, мінімальний CLI та автоматизовані тести.

Обсяг навмисно обмежений базовим інкрементом. Редагування, видалення, пошук/фільтрація, статистика та повний життєвий цикл зміни статусу не реалізовувалися.

## Implementation Summary

- Додано пакет `taskflow` із моделлю Task, SQLite Repository, Task Service та CLI.
- Модель містить `id`, `title`, `description`, `priority`, `status`, `due_date`; назва обов'язкова, опис може бути порожнім, термін виконання може бути відсутнім.
- Репозиторій створює таблицю `tasks`, зберігає завдання параметризованим `INSERT` і повертає всі завдання у порядку `id` за зростанням.
- Сервіс перевіряє дані через модель і делегує збереження/читання репозиторію.
- CLI підтримує `add` та `list`, дозволяє передати шлях `--database` і за замовчуванням використовує `~/.taskflow/tasks.sqlite3`.
- Додано pytest-тести моделі, репозиторію, сервісу й CLI, включно з перевірками некоректного вводу, помилок сховища та збереження між різними запусками.

## Technical Decisions

| Рішення | Обґрунтування |
|---|---|
| Окремий пакет `taskflow/` у корені проєкту | У репозиторії не було пакета застосунку або `src/`; окремий пакет не зачіпає MCP-конектор та інфраструктуру harness. |
| Поділ Model → Service → Repository → SQLite і тонкий CLI | Зберігає межі відповідальностей, зафіксовані Planner та попередньою архітектурою: SQL не потрапляє в бізнес-логіку чи CLI; компоненти можна тестувати окремо. |
| Стандартний `sqlite3` замість ORM | SQLite є прийнятим сховищем; модуль входить до Python, не потребує сервера чи runtime-залежності. |
| `INTEGER PRIMARY KEY AUTOINCREMENT` і `ORDER BY id ASC` | SQLite створює стабільні ідентифікатори, а користувач отримує список у передбачуваному порядку. |
| Окреме короткоживуче з'єднання на операцію, контекст транзакції та гарантоване закриття | Забезпечує commit/rollback і закриття ресурсу без приховування SQLite-помилок. Ініціалізація використовує `CREATE TABLE IF NOT EXISTS` і не видаляє попередні дані. |
| Параметризований `INSERT` | Значення завдання не інтерполюються у SQL; схема обмежує значення priority/status та порожній title. |
| Модель централізує перевірку, сервіс делегує її через створення Task | Однакові інваріанти діють для CLI та прямих викликів сервісу; помилка виникає до запису. Репозиторій не маскує помилки сховища. |
| Значення priority: `low`, `medium`, `high`; status: `planned`, `in_progress`, `completed` | Відповідають наборам з app requirements і зберігаються як однозначні ASCII-значення в БД. |
| Тимчасові дефолти — `medium` і `planned` | Вимоги не задають дефолтів, а базовий сценарій має дозволяти створити завдання без додаткових прапорців. Це практичне припущення реалізації, не підтверджене окремою архітектурною нотаткою; його варто переглянути. |
| `due_date` — optional ISO `YYYY-MM-DD` | Поле передбачене Task Model; nullable та формат лишалися відкритими. Обрано nullable та стандартний ISO date-only для локального першого інкременту. |
| Опис можна передати порожнім, але прапорець `--description` у CLI обов'язковий | FR-01 просить створювати завдання із назвою та описом; Planner зазначив, що вимоги не уточнюють, чи опис мусить містити текст. Тому CLI вимагає поле, але допускає порожнє значення. |
| Шлях БД ін'єктований; CLI за замовчуванням використовує каталог користувача | Виконує рекомендацію Planner не закріплювати дані у робочій директорії проєкту та полегшує ізоляцію тестів. Батьківський каталог створюється за потреби. |
| Тести з pytest та тимчасовими файлами БД | pytest вказаний у вимогах і критерії Planner; тимчасові БД ізолюють користувацькі дані, наявні guardrail-тести теж включені в загальний запуск. |

## Deviations from Plan

- **Не створював `requirements-dev.txt` і не змінював `requirements.txt`.** Planner запропонував окремий файл залежностей, але дозвіл користувача обмежив зміни пакетом `taskflow/`, тестами та `coder-handoff.md`. pytest встановлений лише у віртуальне середовище `.venv`, без зміни файлів проєкту.
- **Початкові значення priority/status визначені як тимчасові припущення.** У Planner handoff їх не було; `medium` та `planned` дозволяють мінімальний сценарій create, але їх треба підтвердити.
- **CLI зроблений підкомандами `add` та `list` на стандартному `argparse`.** Обрано мінімальний UX без сторонніх бібліотек, оскільки вимоги не задавали точного інтерфейсу.
- **Замість власного шару помилок сховища SQLite- та файлові винятки передаються сервісом, а CLI показує явне повідомлення.** Це не приховує причину збою; широких `except` немає.
- Інших відхилень від межі функціональності Planner немає.

## Known Limitations

- Не реалізовано редагування, видалення, фільтри/пошук, статистику, зміну статусу після створення чи інтерактивний CLI.
- Не додано схему міграцій; поточна схема створюється лише якщо таблиця відсутня.
- SQLite-з'єднання відкривається на кожну операцію з файловою БД; режим `:memory:` не підтримується як спільне сховище між операціями.
- Інтерфейс і повідомлення використовують англомовні значення enum; локалізацію не визначено.
- pytest не задекларований у маніфесті залежностей через обмежений дозвіл на зміну файлів; інше середовище має встановити pytest окремо.
- Дефолти `medium`/`planned`, допустимість порожнього опису та формат дати потребують підтвердження власником вимог.

## Corrections After Reviewer Feedback

### Зауваження Reviewer та виправлення

1. **Непогоджені значення `priority` і `status` за замовчуванням (MEDIUM).**
   Вимоги визначають допустимі рівні й стани, але не їхні значення за замовчуванням. Припущення `medium`/`planned` прибрано з моделі, сервісу та CLI: тепер обидва параметри потрібно задавати явно. Так значення не записуються в дані користувача без його вибору.

2. **Невизначена семантика дати завдання (MEDIUM).**
   Вимоги не уточнюють формат і необов'язковість кінцевого терміну. Для першого локального інкременту задокументовано припущення: `due_date` може бути відсутньою; якщо задана — це календарна дата `YYYY-MM-DD` без часу й часового поясу. Це відповідає даті дедлайну та не вводить часову семантику, якої немає у вимогах. Модель перевіряє канонічність і реальність дати; SQLite зберігає її як `TEXT`, а repository повертає її без перетворення. Схема збереження не змінилася, тому міграція не потрібна. Тести перевіряють відхилення timestamp і збереження дати під час round-trip.

3. **Невизначене розташування бази за замовчуванням (MEDIUM).**
   CLI тепер обирає окремий каталог даних користувача відповідно до платформи: Windows — `%LOCALAPPDATA%\TaskFlow\tasks.sqlite3` (із передбачуваним fallback у профіль користувача, якщо змінна відсутня або відносна); macOS — `~/Library/Application Support/TaskFlow/tasks.sqlite3`; Linux та інші платформи — абсолютний `$XDG_DATA_HOME/TaskFlow/tasks.sqlite3` або `~/.local/share/TaskFlow/tasks.sqlite3`. Каталог створюється репозиторієм при відкритті бази, а `--database` і надалі дозволяє явно задати шлях. Вибір каталогу користувача ізолює довготривалі дані від робочої директорії проєкту й не потребує зовнішньої конфігурації.

4. **Відсутня відтворювана dev-залежність pytest (LOW).**
   Додано `requirements-dev.txt` із включенням runtime-залежностей та `pytest>=8,<10`, щоб тестове середовище можна було встановити з маніфесту проєкту.

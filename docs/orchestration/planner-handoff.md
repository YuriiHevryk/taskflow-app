# Planner Handoff

## Task

Підготувати основу модуля керування завданнями TaskFlow на Python із локальним сховищем SQLite. Цей handoff задає Coder межі першої реалізації: створення завдання, його збереження, перегляд списку, валідація та обробка помилок із автоматизованими тестами.

## Requirements

### Підтверджені функціональні вимоги

- **Базовий обсяг першої реалізації з orchestration plan:** створювати завдання, зберігати їх у SQLite, отримувати список завдань, перевіряти введення та обробляти помилки.
- **FR-01:** нове завдання має назву й опис.
- **FR-02:** користувач може переглянути список збережених завдань.
- **FR-10:** завдання зберігаються локально в SQLite і доступні після повторного запуску.
- **CLI:** початковий інтерфейс застосунку має бути командним рядком.

### Підтверджені нефункціональні вимоги

- Застосунок працює локально без постійного доступу до Інтернету.
- Код розділений на модулі за відповідальністю.
- Основні функції покриваються автоматизованими тестами; у вимогах TaskFlow вказаний pytest.
- Некоректне введення обробляється коректно й явно.
- SQLite входить до стандартної бібліотеки Python через `sqlite3`; окремий сервер БД не потрібен.

### Пов'язані вимоги, які слід врахувати, але не вважати реалізованими

- Task Model у базі знань перелічує `id`, `title`, `description`, `priority`, `status`, `due_date`. Рекомендується закласти ці поля в модель і схему першої версії; точні типи, значення за замовчуванням і формат дати є пропозиціями, а не підтвердженими рішеннями.
- **FR-03, FR-04, FR-08, FR-09** (редагування, видалення, пошук/фільтрація, статистика) не належать до першого інкременту. Зберігати в репозиторії чітку межу для подальшого розширення, але не реалізовувати CRUD і статистику понад необхідні операції.
- Зміна статусу та пріоритету (частина FR-05/FR-07) також поза першою функціональною межею; початкові значення для нового завдання потребують узгодження.

## Architecture Context

### Перевірений стан репозиторію

- У репозиторії немає пакета застосунку, `src/` чи наявних Task Model/Repository/Service/CLI модулів.
- Із наявного Python-коду виявлено `connector/server.py` для MCP-доступу до vault та `.github/hooks/pre_tool_guardrail.py`; це інфраструктура harness, не логіка TaskFlow, її не слід розширювати для керування завданнями.
- Єдиний наявний тестовий файл — `tests/test_guardrails.py`; тестів застосунку немає. `requirements.txt` містить `mcp>=2,<3`, але не оголошує pytest.
- У `docs/orchestration/` наявний orchestration plan; чинного Planner handoff немає.

### Компоненти та залежності

Рекомендований напрямок залежностей:

`CLI -> TaskService -> TaskRepository -> SQLite`

`TaskService -> Task model`

- **Task Model** представляє завдання та передає дані між шарами. Він не повинен виконувати SQL або взаємодіяти з CLI.
- **Task Repository** інкапсулює SQLite-запити й перетворення рядків БД на Task. Він відокремлює зберігання від бізнес-логіки.
- **Task Service** виконує валідацію та сценарії створення/перегляду, делегуючи збереження репозиторію.
- **CLI** є тонким адаптером вводу/виводу: збирає аргументи, викликає сервіс і показує результат. Він не містить SQL і не дублює бізнес-правила.
- **Statistics Service** описаний у вимогах застосунку, але не потрібен для базового інкременту й не має створюватися без задачі на статистику.

### Дані

Базова модель за нотаткою Task Model:

| Поле | Рекомендоване представлення | Статус |
|---|---|---|
| `id` | Ідентифікатор, що генерується SQLite; `INTEGER PRIMARY KEY` | Тип і стратегія ID — пропозиція |
| `title` | Непорожній рядок після видалення крайніх пробілів | Обов'язкова вимога до назви; trimming — пропозиція |
| `description` | Рядок; дозволити порожнє значення, якщо інше не вирішить Coder | FR-01 вимагає поле; обов'язковість вмісту не визначена |
| `priority` | Значення з низького/середнього/високого рівнів | Набір рівнів підтверджений FR-05; дефолт не визначений |
| `status` | Заплановано/у процесі/виконано | Набір станів підтверджений FR-07; дефолт не визначений |
| `due_date` | Необов'язкова дата ISO `YYYY-MM-DD` | Поле підтверджене; nullable та формат — пропозиції |

### Архітектурне рішення щодо SQLite

Прийняте рішення **SQLite Storage Decision**: використовувати SQLite, оскільки база локальна, не потребує сервера, надає SQL для пошуку/оновлення, а драйвер `sqlite3` входить до стандартної бібліотеки Python. Доступ до БД належить Task Repository; структура записів має узгоджуватися з Task Model. Не додавати ORM або зовнішній драйвер без окремого обґрунтування.

## Implementation Plan

1. **Створити модель Task.**
   - **Файли:** `taskflow/__init__.py`, `taskflow/models.py`.
   - **Функціональність:** описати типізовану модель із полями Task; визначити представлення пріоритету й статусу без неперевірених довільних значень; додати перевірку інваріантів моделі або чітко доручити їх сервісу, не дублюючи одну й ту саму валідацію.
   - **Залежності:** немає.
   - **Критерій приймання:** модель створюється з валідними даними; невідповідні типи/значення не маскуються; усі поля узгоджені з обраною схемою БД.

2. **Реалізувати SQLite Task Repository.**
   - **Файл:** `taskflow/repository.py`.
   - **Функціональність:** створення таблиці `tasks` під час ініціалізації сховища; методи початкового обсягу для створення запису та отримання всіх завдань; параметризовані SQL-запити; явне відкриття й закриття з'єднань; стабільний порядок результатів (рекомендовано `id` за зростанням).
   - **Залежності:** модель Task.
   - **Критерій приймання:** репозиторій записує та читає всі поля без втрати значень; повторна ініціалізація не стирає наявні дані; список порожній для нової БД; SQL-помилки не перетворюються на успішний порожній результат.

3. **Додати Task Service.**
   - **Файл:** `taskflow/service.py`.
   - **Функціональність:** сценарії створення та перегляду списку; валідація непорожньої назви, пріоритету, статусу та формату дати перед записом; делегування збереження репозиторію; зрозумілий контракт помилок валідації й доступу до даних.
   - **Залежності:** Task Model і Task Repository.
   - **Критерій приймання:** валідне завдання зберігається; невалідне відхиляється до зміни БД; помилки сховища явно доходять до CLI/виклику сервісу.

4. **Під'єднати мінімальний CLI.**
   - **Файли:** `taskflow/cli.py`, `taskflow/__main__.py`.
   - **Функціональність:** команди створення та перегляду завдань; створення залежностей сервісу й репозиторію; показ помилок користувачу без трасування внутрішніх SQL-подробиць. Використати стандартні засоби Python, якщо наявного CLI-фреймворку не виявлено.
   - **Залежності:** Task Service і Task Repository.
   - **Критерій приймання:** `python -m taskflow --help` працює; можна створити завдання, перезапустити команду та побачити його у списку; некоректний ввід повідомляється явно.

5. **Додати автоматизовані тести й декларацію тестової залежності.**
   - **Файли:** `tests/test_task_model.py`, `tests/test_task_repository.py`, `tests/test_task_service.py`, `tests/test_cli.py`, `requirements-dev.txt`.
   - **Функціональність:** pytest-тести моделі, валідації, збереження/читання, помилок та CLI. Для тестів БД використовувати тимчасовий файл або інше ізольоване сховище, не робочу базу користувача. Додати pytest до dev-залежностей, не до runtime-залежностей, якщо обраний формат встановлення це дозволяє.
   - **Залежності:** кроки 1–4.
   - **Критерій приймання:** усі нові тести проходять; запускаються наявні тести guardrails; тести не створюють і не змінюють користувацьку базу даних.

6. **Перевірити інтеграцію та передати результат.**
   - **Файли:** перевірити зміни кроків 1–5; створити `docs/orchestration/coder-handoff.md` відповідно до orchestration plan.
   - **Функціональність:** перевірити весь базовий сценарій через CLI та зафіксувати у Coder handoff перелік змін, відхилення, фактичну команду й результат тестів, відомі обмеження.
   - **Залежності:** кроки 1–5.
   - **Критерій приймання:** Coder handoff відрізняє фактичні результати від припущень; жоден тестовий результат не заявлений без запуску.

## Technical Decisions

| Рішення | Причина |
|---|---|
| Додати окремий пакет `taskflow/` у корені репозиторію | Наявної структури `src/` або пакета застосунку немає; окремий пакет забезпечує модульність без перекроювання MCP-конектора. |
| Розділити модель, сервіс, репозиторій та CLI | Це відповідає попередній архітектурі в app requirements і залежностям нотаток Task Service/Repository/Model; полегшує незалежне тестування та уникнення SQL у CLI. |
| Використовувати стандартний `sqlite3`, не ORM | SQLite — прийняте локальне сховище; вбудований драйвер не додає runtime-залежності й відповідає малому автономному застосунку. |
| У першому інкременті реалізувати лише create/list | Саме ці сценарії прямо визначені як базовий обсяг orchestration plan. Це не створює враження, що весь FR-01–FR-10 або повний CRUD уже покритий. |
| Використовувати параметризовані запити та явний життєвий цикл з'єднань | Захищає значення полів у SQL і запобігає витоку файлових дескрипторів; помилки БД мають бути видимими, а не приховано перетворюватися на порожні результати. |
| Ізолювати тестову БД і тримати pytest у dev-залежностях | Тести мають бути повторюваними та не зачіпати дані користувача; pytest визначений вимогами, але наразі не оголошений у `requirements.txt`. |
| Не створювати Statistics Service, пошук, фільтри, редагування чи видалення в межах цього інкременту | Для них є вимоги на рівні всього застосунку, але немає потреби у базовому сценарії створення/перегляду; уникнення зайвого обсягу не блокує подальше розширення через Repository/Service. |

## Acceptance Criteria

- Можна створити Task із валідними даними через сервіс і мінімальний CLI.
- Запис зберігається в SQLite і доступний після повторного запуску; список повертає всі поля в стабільному порядку.
- Порожня або пробільна назва, невідомий статус/пріоритет і некоректна дата відхиляються з явною помилкою та без часткового запису.
- Операції читання/запису використовують параметризовані запити; помилки SQLite не приховуються під виглядом успіху чи порожнього списку.
- CLI ізолює ввод/вивід від SQL та бізнес-логіки й показує зрозумілі помилки без витоку внутрішніх деталей БД.
- Нові тести перевіряють валідні й невалідні дані, round-trip збереження, порожню БД, повторне відкриття БД, помилки та основні CLI-сценарії.
- `python -m pytest -q` проходить для нових і наявних тестів; точний результат фіксується Coder після виконання.
- Результат не заявляє реалізацію FR-03/04/08/09 або всього TaskFlow, якщо вони не зроблені окремо.

## Test Requirements

- **Model:** створення валідного об'єкта; обов'язковість назви; прийнятні/неприйнятні значення priority/status; optional `due_date` і перевірка формату, якщо Coder приймає ISO-пропозицію.
- **Repository:** створення таблиці; запис/читання всіх полів; порожній список; повторне відкриття тієї самої БД; порядок; некоректний шлях або помилка SQLite передаються явно.
- **Service:** валідація до виклику репозиторію; create/list делегують очікувані операції; помилки валідації та сховища не маскуються.
- **CLI:** help, create, list після створення, некоректне введення; залежності можна підмінити або спрямувати на тимчасову БД.
- Усі тести працюють з ізольованою тимчасовою SQLite-БД; жодна перевірка не залежить від мережі або Obsidian.

## Risks and Constraints

- **Дефолти доменних полів не визначені:** до затвердження нотаток Task Status/Priority не закріплювати неузгоджені дефолти як архітектурний факт.
- **Формат дати та необов'язковість опису не уточнені:** ISO `YYYY-MM-DD` і nullable `due_date` — попередні пропозиції; перевірити їх до реалізації.
- **Шлях до робочої БД не визначений:** зробити шлях ін'єктованим у репозиторій; узгодити CLI-дефолт окремо. Не використовувати реальний файл БД у тестах.
- **Схема першої версії:** якщо змінити типи/назви полів пізніше, знадобиться міграція; не вводити систему міграцій без потреби, але не стирати дані автоматично.
- **Обробка помилок:** не використовувати широке `except` і не повертати порожній список після помилки доступу до БД.
- **Сумісність:** перед додаванням залежностей перевірити наявну структуру; застосунок може використовувати тільки стандартну бібліотеку runtime.
- **Guardrails і межа цієї роботи:** Planner змінює лише `docs/orchestration/planner-handoff.md`; не змінює код, не створює комітів, не виконує push і не записує в Obsidian. Coder має дотримуватися `docs/guardrails.md`; зміни файлів застосунку та архітектури підпадають під затверджений workflow.
- **Неповнота реалізації:** у першому інкременті не включені редагування, видалення, фільтрація/пошук, статистика та повний життєвий цикл статусу.

## Open Questions

1. Які саме дефолти й допустимі значення priority/status визначені в окремих нотатках Task Priority/Task Status? Їх не було серед обов'язкових тем для цього handoff і вони не перевірялися.
2. Чи є опис необов'язковим, і чи має бути `due_date` nullable? Вимоги цього не уточнюють.
3. Чи прийнятний ISO-формат `YYYY-MM-DD` для due date, чи потрібен час/часовий пояс?
4. Де зберігати файл БД за замовчуванням: у робочій директорії, каталозі користувача чи в іншому місці?
5. Під час пошуку нотатки `Task` MCP повернув пов'язані документи/посилання (`Ontology-TaskFlow`, `MOC-TaskFlow`, компоненти), але не окремий текст нотатки `Task`; Coder має уточнити доменне визначення, якщо воно впливає на реалізацію.
6. Чи має перший CLI бути окремими підкомандами, чи достатньо іншого мінімального UX? У вимогах зафіксовано CLI, але командний інтерфейс не деталізований.
